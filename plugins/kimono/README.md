# Kimono

Connect ChatGPT, Codex, or Claude Code to `https://mcp.usekimono.ai/mcp` with
your Kimono account. The plugin bundles the connection and skills; execution
always stays in Kimono's canonical services and authorization boundaries.

## Connect and validate

Use the [installation guide](https://app.usekimono.ai/install) or its
[Markdown version](https://app.usekimono.ai/install.md). If the guide cannot be
fetched, the [repository README](../../README.md) contains the installation
commands. A client-side fetch failure is not proof that Kimono is unavailable.

Start authentication in the host's MCP connection. Open the **complete URL
generated by that host**, preserving its authorization path, query parameters,
PKCE and callback. Never replace it with Kimono's login/home URL or build a
partial `/authorize` URL by hand. Existing platform login is reused; a person
who is logged out signs in and returns to MCP consent before returning to the
host. Do not tell someone to find an approval button on a screen you have not
observed. If the request expires, restart authentication in the host.

The default initial consent requests the supported scopes. Do not add a routine
read-only/full-access question; honor a restriction when the user explicitly
requests it. Never request passwords, cookies, OAuth codes, or tokens in chat,
and leave browser consent to the person.

Validate configuration, OAuth return, tool discovery, `identity_whoami`, and
one relevant authorized read separately. Identity and scopes alone do not prove
all operations work. Do not write merely to test login. Continue the user's
original task after connecting, without asking them to repeat it.

## Product terms and workflows

| Product surface | Skill | Use |
| --- | --- | --- |
| Projeto | `manage-kimono-projects` | Collaborate with selected people, manage participants, and share selected files. |
| Corpus | `manage-kimono-corpora` | Curate sources and files; manage manual upload, connected Google Drive, and Agente grants. |
| Intelligence Layer | `use-kimono-intelligence-layer` | Query authorized Projeto/Corpus content and read evidence; use available governance discussions. |
| Sources | `ingest-kimono-sources` | Upload events and documents to an explicit destination and verify processing/search. |
| Agente | `use-kimono-agents` | Start, continue, and inspect conversations. |
| Builder | `build-kimono-agents` | Create, edit, test, publish, and retire Agentes. |
| Brain | `analyze-with-kimono-brain` | Analyze operational usage, people, conversations, and adoption. |

A Projeto can be one proposal and two people; it does not require a task plan.
Corpus organizes curated sources and currently has an organizational audience.
Both use the same Intelligence Layer. Do not create a mirrored Corpus for each
Projeto or expose internal context-space/graph concepts as extra products.

## Share a proposal with a colleague

“Share this proposal with Marco” authorizes sharing that selected file with
that person, including creating an appropriately scoped Projeto if needed.
Resolve the person through `project_members_search`, inspect candidates with
`project_list`/`project_get` and their members, or create with `project_create`.
Reuse only a Projeto whose audience matches the request. Do not disclose to
additional existing participants or publish to the organization by default.
Direct members do not necessarily enumerate all inherited ACLs; if the effective
audience cannot be established, create a fresh Projeto for the intended people.

Use ingestion with explicit `targetProjectId`, upload only the selected file,
inspect `project_files_list`, then verify search with
`knowledge_search({ focus: "project", projectRef: "project:<uuid>", ... })`
and read by `ref` with `knowledge_read`. Project files can be shared without
sharing the source conversation; preserve explicit conversation selection.
Return the observed file state, participants, and Projeto link when available.
Without a returned or observed URL, provide the Projeto name and ID; do not
invent a platform route. A sharing notification does not prove the recipient
opened or read the file.

Project reads and writes use `projects:read`/`projects:write`, the corresponding
organization MCP permissions, and the Projeto's ACL. Institutional permissions
are not a substitute. Agente use of a Projeto also respects its configured
project context and the person's access.

## Corpus and source management

Use `corpus_*` tools to manage an authorized Corpus, its sources, inventory,
processing, and grants. Read the Corpus/source/file before mutations and
preserve current `accessGeneration`, `syncGeneration`, and `processingVersion`
preconditions. Reconcile an uncertain write before resending.

For Corpus inventory, upload through a `manual_upload` source with
`corpus_upload_prepare` → signed PUT → `corpus_upload_finalize`. A generic
session's `targetSpaceId` does not by itself register the file in that inventory.
Google Drive uses the account already connected to Kimono; the host must not
supply Google credentials or another account's connector. S3 configuration is
not offered. Source pausing keeps already processed content available; archival
revokes Corpus access and retains its records.

Grant replacement sends the complete intended active visible Agente list.
Preserve grants the user did not ask to revoke and do not reactivate revoked
grants without that request. A grant does not configure or publish the Agente.

## Read and verify content

The public read tools are `knowledge_search`, `knowledge_list`,
`knowledge_read`, `knowledge_traverse`, and `knowledge_timeline`. Search/list
use `focus`, selected Corpus references, explicit project references, and the
applicable type/time filters. Use `focus: "corpus"` with `corpusRefs` for Corpus
questions; use `focus: "project"` with `projectRef` for a Projeto.
`current_project` requires runtime context and is not implicit in an MCP host.

Preserve result references and revisions, paginate when needed, and respect
coverage. A document is evidence, not an automatically accepted fact.
`context_share` records governed intent; it is not an upload or a human ACL grant.
Explicit Native/CLI remember/correct/forget operations are not in this gateway.

Accepted event, successful PUT, finalized file, sealed session, document
publication, and successful search/read are separate stages. For institutional
sessions, inspect every attachment with `context_ingest_artifact_status` as
well as the JSONL artifact returned on close; session status does not aggregate
all attachment jobs. A Projeto close can return null artifact/job IDs because
processing is per file. Later semantic interpretation is separate from document
publication. A query error is not normal heartbeat lag.

## Access and recovery

Every operation satisfies OAuth scopes, organization MCP permissions configured
under **Configurações → MCP → Permissões** for the existing dynamic roles, and
the specific resource's ACL. Platform screen visibility is separate. The
server filters tool discovery and revalidates each execution.

`KIMONO_MCP_INSUFFICIENT_SCOPE` requires additional consent. Existing grants do
not automatically gain the new project scopes. `MCP_PERMISSION_DENIED` requires
the relevant organization permission; a resource denial requires its ACL.
Reconnecting does not bypass those boundaries. A project-only grant limits
knowledge reads to authorized Projetos. For existing grants, ingestion can
accept legacy knowledge scopes, but still requires the destination-specific
project MCP permission and Projeto ACL; this is not a workaround for denied
project access. New project connections should request `projects:*`.

An explicit user request for the same target and effect remains valid across
steps; avoid repetitive confirmation questions. Publishing, removal, revocation,
and proposal decisions must match that intent. Host tool approval is separate.

| Recovery | Action |
| --- | --- |
| `retry_read` | Wait the reported delay and retry the read; stop repeated failures and keep diagnostic IDs. |
| `reconcile_before_retry` | Read the resource and establish whether a mutation took effect before resending. |
| `reauthorize` | Complete OAuth through the host-generated authorization URL. |
| `check_permissions` | Check organization MCP permission and resource ACL. |
| `refresh_state` | Read the current revision/generation before changing it. |
| `investigate` | Keep the error and correlation IDs; do not invent a cause or retry blindly. |

For an uncertain Builder patch, inspect `agents_draft_get` and `agents_diff`
before using the current revision. `No approval received` without a Kimono
envelope suggests host approval but does not prove the origin or server
execution. Keep `requestId`, `operationId`, `deploymentId`, and `phase` when
returned. Poll turns and previews with `turns_get` until `terminal: true`.

## Update and host manifests

Version **0.5.0** adds Projeto collaboration guidance, updates the current
Intelligence Layer read contract, and clarifies host-generated OAuth consent.
Deploy the matching Core/MCP release, update the installed plugin, reload its
skills, and refresh the remote tool catalog. These are separate steps. A skill
alone does not prove a tool is available or authorized; do not invent private
API fallbacks when the catalog lacks it.

The `.codex-plugin/plugin.json` and `.claude-plugin/plugin.json` manifests use
the same `skills/` and `.mcp.json` so behavior and authorization stay aligned.
Public directory submission is a separate release action.
